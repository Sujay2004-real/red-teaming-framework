What already holds up

  • The policy engine is the real thing — per-tool flag enumeration, fail-closed, with the exploitation gate re-checked at plan, draft and approval time. That layering is the hardest part to get right and it is right.
  • Test depth where it counts. 233 tests that assert refusals, not just successes — msfconsole script validation, payload-flag gating, IPV6 scope containment, provider-outage fallback.
  • Prompt-injection discipline. Tool output stripped, confined to untrusted blocks, authorization never derived from it, AI citations verified against real finding ids.
  • The UI has genuine responsive work — breakpoints at 850/520px and two prefers-reduced-motion blocks. More than most projects at this stage.

Where it is thin

  • One 1,493-line module doing routing, orchestration, serialization and startup migration. It is the file most likely to break and the hardest to test in isolation.
  • Zero frontend tests against ~2,700 lines of UI. The policy engine has 40 tests; the plan editor has none.
  • 13 unpinned dependencies and no lockfile. Your reproducibility claim in the report rests on a pip install that resolves differently every month.
  • The letter's authority is trusted as parsed. Everything downstream — including whether exploitation is allowed at all — rests on engagement_parser.py, which has 8 tests and no adversarial ones.

Correctness — fix these first

9 findings

Latent bugs that are live in the code today. Three of them sit inside security-relevant paths, which is why they lead the list.

Duplicate ZAP alert lines resolve to the wrong URLs

High analyzer.py:693

Why The detail-line scan re-splits the whole output and calls .index(line) to find its own position — that returns the first occurrence, not the current one. When ZAP reports the same rule name twice with different URLs, the second alert inherits the first alert's URL block, so findings name the wrong endpoint. It is also O(n²): three full splits of the transcript per matched alert.

Fix: iterate once with enumerate(stdout.splitlines()), keep the index, and slice from idx + 1. Two lines changed, both bugs gone.

The curl payload-flag set is duplicated inline in the gate

High main.py:677–685

Why create_assessment hardcodes its own literal set of curl body flags instead of importing PAYLOAD_FLAGS from phases.py. Two copies of a security-relevant constant drift: add a flag to one and the plan-time gate and the approval-time gate disagree about what counts as exploitation. That is precisely the class of bug the three-layer gate exists to prevent.

Fix: import PAYLOAD_FLAGS and reuse policy_engine._command_uses_payload_flag. One source of truth.

The auto-recommendation task can be garbage-collected mid-flight

High main.py:1054, 1255

Why schedule_auto_recommendations returns the task from asyncio.create_task, and the caller discards it. asyncio holds only a weak reference, so the batch can vanish before it writes — an intermittent "the recommendation just didn't appear" bug that will be near-impossible to reproduce on demand.

Fix: keep a module-level set() of pending tasks, add on create and discard in a done-callback. Standard asyncio hygiene, ~4 lines.

Recommendation payload fields shadow the serialized record

Medium main.py:1084

Why **(record.payload or {}) splats last, so a payload carrying id, phase or origin silently overwrites the authoritative column values. The API contract becomes dependent on what the provider happened to emit.

Fix: splat first, then set the columns explicitly — or nest it as 'payload': record.payload or {}.

Scoped SSH transcript re-joined on every poll

Medium ssh_executor.py · _run_blocking

Why Each 1-second poll does _exit_code(''.join(chunks), token) — rebuilding the growing transcript from scratch. An nmap sweep producing a few hundred KB means hundreds of full concatenations, on the thread streaming your live terminal.

Fix: join once outside the loop and append only the new chunk each pass, or check the marker against just the tail window — the exit marker is always near the end.

Target address has no uniqueness constraint behind the check

Medium database.py · Target

Why create_target does query-then-insert on scope_domain_ip, but the column has no unique=True. Two concurrent requests both see "no row" and both insert. Duplicate targets then split findings across two assessment histories — and your test suite already asserts dedupe behaviour, so the contract is intended.

Fix: unique=True on the column plus a catch-and-return-existing on IntegrityError. ToolExecution already models this correctly with its composite constraint.

Foreign keys carry no ON DELETE CASCADE

Medium database.py · all models

Why Every cascade is hand-written in application code. That is why Recommendation had to be added to the delete path by hand, and why test_level2_recommendations_die_with_the_assessment exists as a regression guard. The next table added will be forgotten the same way, leaving orphaned rows in the engagement evidence you cite in your report.

Fix: ondelete='CASCADE' on the FKs plus SQLite's PRAGMA foreign_keys=ON per connection. The manual cleanup can then stay as belt-and-braces.

Recommendation recording swallows every exception

Medium main.py:1000–1043

Why A bare except Exception: db.rollback(); return None with no log line. The read-only loop is designed to fail quietly so it never blocks execution — correct instinct — but silence means a persistent provider or schema fault looks identical to "no proposals this round".

Fix: keep the swallow, add one logger.warning(..., exc_info=True). Behaviour unchanged, diagnosability restored.

Startup work runs at import time

Low main.py:258 · database.py

Why _ensure_operator_key_at_startup() fires at module import, and database.py runs _migrate_sqlite() and _encrypt_stored_secrets() the same way. Anything that imports the module to inspect it — a test collector, a linter, a REPL — mutates the database and the secret key. It also makes the app untestable without filesystem side effects.

Fix: move all three into a FastAPI lifespan handler. This pairs naturally with adding Alembic (see optimization).

Code optimization

11 findings

Structural work. None of it is on fire, but the first three are cheap wins and the main.py split pays for itself the moment you touch the API again.

The policy engine rebuilds its entire capability table on every call

Medium policy_engine.py:327

Why tool_registry() constructs the full nested dict — ~265 lines of per-tool flag tables — fresh on each call, and validate_command calls it every time. The planners then call validate_command once per candidate in a loop. A dozen candidates means a dozen rebuilds of a constant.

Fix: return a module-level frozen mapping built once. In the same edit, move the capabilities data into tool_capabilities.py so the 265 lines of tables stop burying the logic.

Next-steps provenance check is quadratic

Medium next_steps.py · _verified_provenance

Why The verified-id list is rebuilt with a list comprehension inside the per-candidate loop, so it is O(candidates × findings). Small today; it scales with engagement size, and this runs on every completed execution in the automatic loop.

Fix: build the id set() once before the loop.

Encryption key re-read from disk on every operation

Low secret_store.py · _load_key

Why _load_key() is deliberately uncached, so every encrypt and decrypt costs a filesystem read. The comment suggests this was a considered choice, but it is not documented why, and a per-process cache with an explicit invalidation on key rotation gives the same safety.

Fix: either cache with functools.lru_cache and a documented clear() hook, or write down the reason it must stay uncached. Undocumented is the only wrong answer.

A database round-trip on every authenticated request

Low api_auth.py · verify_operator_key

Why The operator digest is queried from AppSettings for each request, including the 1-second live-terminal poll — so the UI generates a DB read per second while a command runs.

Fix: a short-TTL cache (5 s) invalidated on the settings-write path. Note the env-var override must stay checked first.

SQLite runs with default pragmas under concurrent writes

Medium database.py · create_engine

Why No WAL, no busy_timeout, no pool_pre_ping. The live-terminal poll reads while the executor writes findings and the recommendation thread writes batches. Under that overlap SQLite's default rollback journal will raise database is locked — the kind of failure that appears only during a live demo.

Fix: a connect event listener setting journal_mode=WAL, busy_timeout=5000, foreign_keys=ON, synchronous=NORMAL. Four lines, removes a whole failure class.

One module owns routing, orchestration, serialization and startup

Medium main.py · 1,493 lines

Why 21 endpoints, the assessment lifecycle, the approval-and-execute path, phase orchestration, four serializer functions and import-time migration all in one file. create_assessment alone does six jobs: brief assembly, AI planning, restricted-tool filtering, exploitation gating, normalization and persistence. Every change touches the file everything else depends on.

Fix: split into routers/ (targets, assessments, execution, settings, reports), lift the serializers to serializers.py, and extract an AssessmentService. Do it without behaviour change and the existing 233 tests are your safety net — which is exactly what they are for.

The provider call and fence-stripping are written three times

Medium analyzer.py:765 · planner.py · next_steps.py

Why analyzer._ai_findings hand-rolls the OpenAI-compatible POST, and planner._strip_fence and next_steps._strip_fence are near-identical. Three places to fix when a provider returns a slightly different envelope, and three chances for the timeout or the payload bound to differ.

Fix: one llm_client.py exposing chat_json(...) that owns the request, the timeout, the fence-stripping and the size bound. The three callers keep only their prompts and their fallbacks.

Schema changes are hand-rolled ALTER TABLE at import

Medium database.py · _migrate_sqlite

Why No Alembic, so every column added means another manual ALTER TABLE ADD COLUMN guarded by an introspection check, executed on import. There is no downgrade path and no record of what version a given database file is at — which matters if you demo from a database created weeks ago.

Fix: adopt Alembic, generate an initial revision matching current schema, and keep the hand-rolled path as a one-shot compatibility shim. Trigger from the lifespan handler.

Plan equality is key-order sensitive

Low frontend/src/lib/constants.js · samePlan

Why samePlan compares via JSON.stringify, so the same plan serialized with keys in a different order reads as dirty — leaving the save button enabled when nothing changed, and making planDirty unreliable.

Fix: compare the fields that matter explicitly (tool, command, reason, length). Cheap, and it makes the dirty state trustworthy.

Derived booleans recomputed on every render

Low frontend/src/App.jsx

Why planLocked, executedPrefixIntact, planEditable, canAnalyze and canReport are plain expressions re-evaluated on each render — and the 1-second live-terminal poll re-renders App, so they recompute every second while a command runs.

Fix: useMemo the derived flags, and move the live-terminal poll into its own component so the 1 Hz tick stops re-rendering the whole tree. The phase memoization you already have shows the pattern.

Serializer functions are dense single-line dict literals

Low main.py:59–123

Why serialize_target, serialize_assessment, serialize_execution and serialize_finding are long unbroken lines — hard to review, and hard to confirm at a glance that a secret field has not crept into the response.

Fix: one key per line, and add a test that asserts no api_key/password/secret key can appear in any serialized payload. You have that guarantee today by inspection; make it a test.

Security hardening

4 findings

The core is sound. These four are about the edges — the letter, and what happens when a dependency changes under you.

The engagement letter's authority is trusted as parsed

High engagement_parser.py · 424 lines, 8 tests

Why This module decides what is in scope, which tools are restricted, and whether exploitation is authorized. Everything downstream inherits its verdict, and the exploitation gate is only as strong as the parse. Its eight tests are all well-formed letters — there is no adversarial case: a letter naming a host outside the declared subnet, contradictory allow/deny sentences, a target list that resolves to a wider CIDR than intended, or a crafted document that smuggles an extra target into the table.

Fix: add adversarial parser tests, and — more valuable — surface the parsed scope back to the operator for explicit confirmation before any plan is generated. The human is already in the loop for commands; put them in the loop for authority too.

Thirteen unpinned dependencies and no lockfile

High backend/requirements.txt

Why fastapi, sqlalchemy, pydantic, paramiko, cryptography and the rest all float. Two consequences: the Docker image built for your evaluation is not the one you tested, and — for a security tool — you inherit upstream CVEs silently. A framework that gates sqlmap behind a letter should know what version of its own HTTP client it is running.

Fix: pin exact versions and add pip-compile (or uv) to produce a hashed lockfile. Add Dependabot. This is also what makes your Chapter 8 numbers reproducible by anyone else.

Focus ring is a box-shadow, invisible in High Contrast Mode

Medium App.css:199, 805

Why Inputs set outline: none and substitute a box-shadow on focus. Windows High Contrast Mode discards box-shadows, so keyboard users on your own laptop's accessibility settings lose the focus indicator entirely. Note .dropzone gets this right — it uses a real outline.

Fix: replace outline: none with :focus-visible { outline: 2px solid var(--accent); outline-offset: 2px } and keep the shadow as an enhancement.

No dark mode despite a token-ready stylesheet

Low App.css · :root

Why Eleven custom properties already define the palette, so the groundwork is done — but a good number of rules still use literal colors like #cbd5de and #fff inline. A security operator staring at a live terminal at 2 a.m. will want a dark surface, and the audit trail is a lot of text.

Fix: sweep the literals into tokens first (a mechanical pass), then add a prefers-color-scheme block plus a manual toggle. Doing the sweep first means the dark theme is one block, not two hundred edits.

UI and UX

8 findings

The interface is more considered than most at this stage — tab semantics, aria-pressed, reduced-motion handling. These are the gaps that remain.

No error boundary anywhere in the tree

Medium frontend/src/App.jsx

Why One unexpected value in a nested component — a null restricted_tools, a finding missing a field — unmounts the entire application to a blank white page. During a live demo that is unrecoverable without a reload, and a reload loses the in-flight assessment view.

Fix: a small ErrorBoundary around the workspace, rendering the error and a "reload workspace" button. Twenty lines and it turns a demo-ending failure into a recoverable one.

Validation failures arrive as backend errors, not field feedback

Medium NewAssessmentPanel.jsx · TargetPanel.jsx

Why Pydantic enforces real bounds — 50 scopes, 255 chars, 256 addresses, usable URL schemes — but the UI only discovers a violation after a round-trip, and reports it as a generic banner. The operator cannot tell which field is wrong or what the limit is, so they guess and resubmit.

Fix: mirror the bounds as client-side maxLength/counters, and map a 422's loc back onto the offending field instead of the banner. The "characters left" counter in the prompt form is exactly the right pattern — extend it.

The plan is locked while a command runs, with no explanation

Medium PlanEditor.jsx · planEditable

Why The append-only invalidation rule — executed steps freeze, new steps append — is the most interesting design decision in the project, and the UI presents it as a dead input. A new operator reads a disabled editor as "broken", not as "the audit trail is immutable".

Fix: replace the disabled state with a short line of copy on the frozen prefix — "Steps 1–4 executed; they are sealed as audit evidence. Append new steps below." The constraint is a feature; say so.

Live terminal re-renders the whole application at 1 Hz

Low App.jsx · live poll effect

Why The poll updates state on App, so every second the entire tree — plan editor, findings, audit trail, phase pipeline — reconciles. With a large audit trail this is visible jank on your i3, right when the operator is watching the output most closely.

Fix: move the poll into a LiveTerminal component owning its own state. The rest of the tree stops re-rendering entirely.

2055 lines of global CSS with no layering

Low frontend/src/App.css

Why One global stylesheet for 16 components, with element-level selectors (header, input) sitting alongside component classes. Specificity collisions are already a risk, and there is no way to delete a component's styles with confidence.

Fix: surgical, not a rewrite — keep the tokens in a tokens.css and split the rest per component area. The existing BEM-ish class names mean this is mostly cut-and-paste.

The sidebar/workspace split is tight for the demo laptop

Low App.css · .workspace, breakpoint 850px

Why Above 850px the grid is 350px 1fr. On an 8 GB i3 laptop at 1366×768 with browser chrome, that leaves under 700px for the plan editor and the live terminal — the two densest views — before the breakpoint stacks them. Worth checking at that exact size rather than assuming.

Fix: either raise the breakpoint to ~1000px, or make the sidebar collapsible with a toggle. Test at 1366×768 specifically, since that is the machine this runs on.

Vite scaffolding left in the tree

Low frontend/src · assets

Why The default react.svg, vite.svg and a one-line index.css are still present and unreferenced. Small, but they are the first thing a reader of your repository notices, and they signal a template that was never cleaned up.

Fix: delete them. Confirm favicon.svg is the one actually linked in index.html.

No empty, loading or partial-failure states

Low FindingsPanel · AuditTrailPanel · CrewPanel

Why Panels render their content when data exists and nothing when it does not. A blank findings panel after a completed scan is ambiguous: no findings, or analysis not run? During your evaluation runs this ambiguity will cost you real time.

Fix: explicit empty states that name the next action — "No findings yet. Run Analyze after executing a step." This is also the cheapest way to make the tool feel finished.

Testing and CI

6 findings

Your backend suite is genuinely good. The gaps are all on the frontend and in what CI actually verifies.

Zero frontend tests against 2,700 lines of UI

High frontend/package.json · no test script

Why App.jsx holds ~30 state hooks and the entire request lifecycle. The most intricate logic in the project — the executed-prefix freeze, plan-dirty detection, phase unlock — is untested and lives in the file that changes most. A Vite+Vitest setup is a ten-minute install.

Fix: add Vitest + Testing Library, and start with three pure-logic tests (samePlan, the prefix-integrity check, suggestedObjective) plus one render test of PlanEditor's frozen state. Highest ratio of confidence to effort available anywhere in this list.

CI builds the frontend but never lints it

Medium .github/workflows/ci.yml

Why npm run lint exists, is configured with the hooks and refresh plugins, and is never invoked. Your report cites "ESLint: 0 errors" as a verified fact, but nothing enforces it — so the claim decays from the next commit onward.

Fix: add the lint step. One line, and it makes an existing claim in your report permanently true.

CI never builds the Docker images or runs the smoke test

Medium .github/workflows/ci.yml · smoke_e2e.py

Why Tests run against a bare pip install on the runner, which proves nothing about the image that actually ships — and the scanner binaries exist only inside that image, so the highest-risk part of the build is the part CI never touches. smoke_e2e.py exercises the full lifecycle and is never run automatically.

Fix: add a job that does docker compose build, and run smoke_e2e.py against the local engine. That is the check that would have caught the payload-flag drift and the SQLite locking above.

No Python linter, formatter or type checker

Medium repository root · no pyproject.toml

Why There is no pyproject.toml, no ruff/black config, no mypy, no pre-commit. For a codebase whose correctness argument rests on validating untrusted input, the absence of static checking on the Python side is the single biggest asymmetry in the project's quality posture.

Fix: ruff (lint + format) and mypy in non-strict mode, wired into CI and pre-commit. Ruff alone will surface unused imports and shadowed names across all 9,300 lines in seconds.

CI has no caching and tests one Python version

Low .github/workflows/ci.yml

Why Every run reinstalls all 13 packages from scratch, and only 3.10 is exercised — despite the README claiming 3.10+. A user on 3.12 is untested.

Fix: actions/setup-python and setup-node caching, plus a 3.10/3.12 matrix. Cuts run time and makes the version claim real.

The executor's subprocess path has no direct tests

Low backend/modules/executor.py

Why ssh_executor.py is tested thoroughly, including timeouts and pane serialization. The local engine — the one that actually runs on the demo machine — has no equivalent coverage of its timeout, output cap or the os.killpg termination path.

Fix: mirror the SSH test shape for the local engine: a long-running command hitting EXECUTION_TIMEOUT_SECONDS, an oversized output hitting LIVE_BUFFER_CHARS, and confirmation that the env allowlist excludes everything else.

Since this file is the context document for AI-assisted development, a stale map is worse than no map: it directs future work at the wrong files.

Six scratch scripts and three generated PDFs at the root

Why Five make_*.py scripts (several tens of KB each) and three generated PDFs currently sit untracked in the working tree. They are report-generation tooling, not application code, and they clutter the root next to main.py and package.json.

A nested git repository is gitignored as a "placeholder"

Low .gitignore:68 · red-teaming-framework/

Why The name suggests an earlier attempt at this same project, kept as an empty nested repo. Nested repos confuse tooling and readers alike, and a reviewer will ask what it is.

README at 42 KB is doing four documents' work

Suggested order

4 passes

Sequenced so that each pass makes the next one safer. The first is a single sitting.

  1. Pass one Close the live bugs ZAP duplicate-line index, the duplicated payload-flag set, the GC-able task, the payload splat, the SQLite pragmas. All five are small, local edits with existing tests around them — do them before anything else.
  2. Pass two Make the claims enforceable Pin dependencies and add a lockfile, add ruff + mypy, add the missing lint step to CI, add Vitest with the three logic tests. This is the pass that makes every quality statement in your report true by construction rather than by inspection.
  3. Pass three Harden the edges Adversarial engagement-parser tests, operator confirmation of parsed scope, the error boundary, real focus-visible outlines, the unique constraint and FK cascades. This is the pass that protects the demo.
  4. Pass four Pay down structure Split main.py into routers, extract llm_client.py, add Alembic, sweep CSS literals into tokens, split the README. Do this last and only with the test suite as your safety net — it is the largest change and the least urgent.
